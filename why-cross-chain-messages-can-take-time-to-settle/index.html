Why cross-chain messages can take time to settle

Cross-chain transfers wait because the destination chain needs proof that the source action is settled, plus a verifier and transaction to accept and execute it.

The Chain Times DeskOct 16, 2026 · 22:04 UTC3 min read

Cross-chain messages can delay settlement because the destination chain must verify what happened on the source chain before it acts. A transfer may look complete on one chain while its message is still waiting for proof, checks or execution on the other. These steps help prevent the destination from acting on a transaction that could be reversed or is not valid.

The exact path depends on the bridge or messaging system. If you are comparing that process with a swap, this guide to Quickswap’s first cross-chain swap covers how to make one. The general point is that sending a message and settling its result are separate steps.

What has to happen before a message is settled?

The source transaction must first be included in a block. The messaging system then waits for enough source-chain confirmations — later blocks that make a change harder to undo — before treating the transaction as reliable. LayerZero’s documentation shows that applications can set different confirmation counts for each direction between chains.

After that, a verifier checks the message. In LayerZero, these verifiers are called Decentralized Verifier Networks (DVNs). In Hyperlane, the destination mailbox checks the message against its Interchain Security Module (ISM), a rule set that decides what proof is acceptable. Hyperlane’s documentation says a relayer gathers the needed signatures or proofs and submits the message for processing.

Even after verification, the destination chain needs a transaction to run the message. That transaction must be submitted and included on the destination chain. If the message calls a contract that needs more gas than provided, execution can fail and may need another attempt. Verification and execution are related, but they are not the same event.

Why do some transfers take longer than others?

Each step can add waiting time, and the slowest one sets the pace. A system that waits for more source-chain confirmations may take longer before verification can begin. A verifier that needs several independent signatures must wait until its rules are met. Then the destination transaction must get its turn on that chain.

Some bridges also use an optimistic design: they accept a claim first and allow a challenge period before funds can be withdrawn. That delay serves a different purpose from gathering signatures. For example, Optimism’s documentation describes a finalization period for withdrawals from its network to Ethereum. So “bridge time” can mean either a short wait for message verification or a longer wait built into the bridge’s security model.

What should you check when a transfer is pending?

Look up the transaction on both chains and identify its current stage. A source-chain confirmation does not prove that destination execution has finished. Bridge status pages often separate these steps, and protocol documentation explains what each status means.

  • Source chain: Is the transaction included, and has it reached the required confirmations?
  • Verification: Does the bridge show the message as verified, or is it waiting for a proof or signatures?
  • Destination chain: Has a transaction been submitted and included, or did execution fail?

If the message is verified but the destination action is still pending, the remaining delay may be execution rather than security review. The useful takeaway is to check the stage before judging the wait: a single “pending” label can hide several separate steps.
