BTC swap API integration: bridge and vault routes compared

TeleSwap vs THORChain API: THORChain routes BTC to native assets; TeleSwap mints teleBTC on EVM and can swap it, giving app developers two distinct integration paths.

The Chain Times DeskNov 27, 2026 · 08:02 UTC3 min read

TeleSwap and THORChain take different routes for app BTC swaps: THORChain sends native BTC through validator-run vaults to native assets, while TeleSwap verifies a Bitcoin deposit and mints teleBTC on an EVM chain, with an optional swap.

  • Choose THORChain for native assets on non-EVM chains; its vault flow pays out across many chains.
  • Choose the Bitcoin bridge for BTC-backed tokens on EVM chains; it delivers teleBTC or a swapped token.
  • Keep THORChain inbound details fresh; vault churn can retire an address after its quote expires.
  • Block exchange-account deposits for THORChain; failed swaps refund to the source BTC address.

TeleSwap suits EVM tokens; THORChain suits native assets

Start with the asset your app must deliver, because that decides the deposit flow and the failure destination. For the EVM route, use TeleSwap when your app needs a Bitcoin-backed token or a DEX-swapped token on a supported EVM chain.

THORChain starts with a fresh quote. The quote returns an inbound vault address, a memo and an expiry. Send the BTC to that address with the memo attached. THORChain validators run the vaults, and vaults can churn, so caching an inbound address past the quote expiry risks sending BTC to a retired vault.

The EVM deposit has different inputs: send BTC to a Locker address with the request data encoded in an OP_RETURN output. A Bitcoin relay contract verifies the on-chain deposit. The destination result is teleBTC, or a token received after an optional swap.

  • THORChain: the inbound address and memo route the quoted swap; native assets arrive on the selected supported chain.
  • The Locker flow: the Locker address and OP_RETURN request identify the deposit; teleBTC or a DEX-swapped token arrives on a supported EVM chain.

Failure handling changes what your app must tell users. THORChain refunds a failed BTC swap to the sending BTC address. If a user deposits from an exchange account, the refund would go to the exchange’s wallet, not necessarily back to an address the user controls. Block exchange-account deposits for this flow, or require a source address that can receive the refund.

For the Locker route, a failed swap falls back to teleBTC on the destination chain. That gives the app a token outcome to handle instead of a BTC refund to the source address.

What does a THORChain swap memo contain?

A THORChain swap memo carries the swap request for the inbound BTC, including the destination asset and destination address. Pair it with the vault address and expiry from the fresh quote.

What is teleBTC?

teleBTC is a Bitcoin-backed token minted on an EVM chain after the Bitcoin deposit is verified through the relay contract. The app can deliver it directly or swap it for another supported EVM token.

Consider two otherwise identical apps with the same BTC deposit and swap need. When the target is a BTC-backed token on EVM, the Locker route fits; change only the target to a native asset on a non-EVM chain, and THORChain fits. Choose based on that destination constraint, and keep its corresponding failure path visible to users.
